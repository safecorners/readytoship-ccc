## Context

동기는 `proposal.md`를, 행위 계약은 `specs/deploy-pipeline/spec.md`를 참조한다. 이 문서는 그 요구를 어떤 구성으로 만족시킬지만 다룬다.

설계를 제약하는 현재 상태 — 모두 실측으로 확인한 것이다.

- Vercel 프로젝트 `safecorners/readytoship-claude-code`가 GitHub 저장소에 연결돼 있다. Next.js 프리셋, Node 24.x, 빌드 명령 `npm run build`. 프로젝트 설정은 Vercel 대시보드에만 있고 저장소에는 없다.
- `main` 병합 → 프로덕션, 브랜치 push → 프리뷰가 이미 동작한다. 프로덕션 주소는 `https://readytoship-ccc.vercel.app`로 고정돼 있다.
- Vercel은 커밋에 `Vercel` 컨텍스트로 상태를 올린다. 병합된 커밋에서 `state=success`를 확인했다.
- `main`에 브랜치 보호가 없다. `GET /branches/main/protection`이 `404 Branch not protected`를 준다.
- **`next build`는 ESLint를 돌리지 않는다.** 빌드 로그에 lint 단계가 없다. `npm run lint`는 별도로 `eslint`를 실행한다.
- 콘텐츠 검증은 빌드 중 서버에서 돈다. 식별자 중복과 본문 파일 부재 양쪽에서 빌드가 실패하는 것을 확인했다.

## Goals / Non-Goals

**Goals**

- 이미 동작하는 배포 경로를 건드리지 않고 계약만 얹는다
- 병합 게이트가 빌드와 린트를 모두 덮되, 같은 빌드를 두 번 돌리지 않는다
- 배포 규칙을 저장소에서 읽을 수 있게 한다

**Non-Goals**

- **빌드 설정을 `vercel.ts`로 옮기지 않는다.** 대시보드 설정이 지금 정확하게 동작하고 있어, 코드로 옮기는 작업은 순수한 이득이 아니라 깨뜨릴 위험을 안고 얻는 재현성이다. 배포가 불안정해지거나 설정이 늘어나 추적이 어려워지는 시점에 별도 change로 다룬다.
- **Node 버전을 고정하지 않는다.** Vercel은 24.x, 로컬은 22.22.2로 갈라져 있다. 지금까지 이 차이로 문제가 난 적이 없고, `package.json`의 `engines`를 건드리는 것도 위 항목과 같은 성격의 작업이라 함께 미룬다. 다음 change의 실마리로 여기 적어 둔다.
- 배포 알림, 롤백 자동화, 성능 예산 같은 파이프라인 확장

## Decisions

### 1. 게이트를 Vercel 상태 + Actions 잡 둘로 나눈다

필수 상태 체크 두 개를 건다.

| 체크 | 출처 | 덮는 것 |
|---|---|---|
| `Vercel` | Vercel Git 연동이 자동으로 올림 | 프로덕션 빌드, 콘텐츠 검증 |
| lint 잡 | 새로 추가하는 GitHub Actions | ESLint |

**왜 나누는가.** Vercel은 이미 PR마다 배포를 만들고 그 결과를 커밋 상태로 올린다. 그 빌드가 콘텐츠 검증까지 포함하므로, 필수로 걸기만 하면 새로 만들 것이 없다. 반면 린트는 그 빌드에 들어 있지 않다 — Next 16의 `next build`가 ESLint를 돌리지 않기 때문이다. 그래서 린트만 따로 붙인다.

**대안: Actions에서 build와 lint를 모두 돌리기.** 저장소 안에서 검증이 완결된다는 장점이 있지만, 매 PR마다 빌드가 두 번(Actions + Vercel) 돈다. Vercel 빌드는 어차피 프리뷰 배포를 위해 반드시 돌아야 하므로 Actions 쪽 빌드는 순수한 중복이다.

**대안: `Vercel` 하나만 필수로 걸기.** 새 파일이 전혀 없다는 점은 매력적이지만, 린트 오류가 그대로 통과한다. 스펙의 "정적 분석" 요구를 만족하지 못한다.

### 2. Actions 잡은 lint만 돌린다

`.github/workflows/lint.yml`은 `pull_request`에서 `npm ci` → `npm run lint`만 실행한다. 빌드를 넣지 않는 이유는 결정 1과 같다.

잡 이름은 브랜치 보호의 필수 체크 이름으로 그대로 쓰인다. 잡 이름을 바꾸면 필수 체크가 영영 오지 않는 체크를 기다리게 되므로, 이름을 바꿀 때는 보호 설정도 함께 고쳐야 한다. 그 사실을 워크플로 파일 주석에 남긴다.

### 3. 브랜치 보호는 워크플로가 `main`에 올라간 뒤에 켠다

순서를 뒤집으면 보호 설정이 아직 존재하지 않는 체크를 기다리며, 그 워크플로를 도입하는 PR 자신이 병합되지 못한다.

따라서 이번 change는 파일 변경(워크플로, README)을 먼저 병합하고, 브랜치 보호는 병합 후 저장소 설정으로 켠다. 브랜치 보호는 파일이 아니라 git 히스토리에 남지 않으므로, 어떤 값으로 켰는지 README에 적어 둔다.

### 4. 프리뷰 보호를 유지하고 스펙을 거기에 맞춘다

구현 중에 드러난 것이다. 프리뷰 배포는 Vercel Deployment Protection 뒤에 있어 인증되지 않은 요청은 `vercel.com/sso-api`로 302된다. 응답 헤더에 `x-robots-tag: noindex`도 붙는다.

처음 쓴 스펙은 "검토자가 병합 전에 실제 화면을 열어볼 수 있다"고만 했고, 누구를 검토자로 보는지는 말하지 않았다. 실제로는 Vercel에 로그인한 사람만 열린다.

보호를 끄는 대신 스펙을 좁혔다. 공개 저장소이긴 하나 아직 병합되지 않은 문구가 공개 주소로 돌아다니고 검색에 잡히는 것은 튜토리얼 사이트에서 득이 없다. 검토자가 소유자 한 명인 지금 구성에서 보호는 마찰을 만들지 않는다.

`specs/deploy-pipeline`의 프리뷰 요구에 열람 제한과 검색 노출 금지를 명시하고, 권한 없는 접근이 내용을 보지 못한다는 시나리오를 더했다. 계약이 실제 동작과 어긋난 채로 남는 것이 가장 나쁘다.

### 5. 문서는 README에 둔다

배포 규칙을 찾는 사람이 가장 먼저 여는 자리다. 별도 `docs/deployment.md`를 만들면 README에서 한 번 더 건너뛰어야 하고, 이 저장소 규모에서 그럴 만큼의 분량이 아니다.

## Risks / Trade-offs

**`Vercel` 필수 체크가 병합을 멎게 할 수 있다** → 배포가 만들어지지 않는 커밋에서는 상태가 영영 오지 않는다. 문서만 고치는 PR에서도 Vercel은 배포를 만들기 때문에 실제 위험은 낮다. 완화: 막히는 경우 관리자 우회로 푼다(Open Question 1과 연결).

**브랜치 보호는 되돌리기 쉽고 흔적이 남지 않는다** → 파일이 아니라 저장소 설정이라, 누가 끄면 git에서 알 수 없다. 완화: 설정값을 README와 이 문서에 적어 두고, 스펙의 병합 게이트 요구를 검수 기준으로 남긴다.

**PR을 강제하면 1인 작업의 마찰이 늘어난다** → 지금까지도 PR을 거쳐 왔으므로 실질 변화는 "체크를 기다린다"는 것뿐이다. Vercel 빌드가 30초 안쪽이라 대기는 짧다.

**Vercel의 상태 컨텍스트 이름에 의존한다** → 필수 체크를 `Vercel`이라는 문자열로 건다. Vercel이 이 이름을 바꾸면 게이트가 조용히 통과되는 것이 아니라 영영 대기 상태가 되므로, 실패하는 방향이 안전한 쪽이다.

## Migration Plan

기존 동작을 바꾸지 않는다. 배포 파이프라인은 그대로 돌고, 병합 전 조건만 추가된다.

되돌리기: 브랜치 보호를 끄면 즉시 이전 상태다. 워크플로 파일과 README는 되돌려도 배포에 영향이 없다.

## Open Questions

1. **관리자 우회를 허용할지** — 검토를 받아 **`enforce_admins: false`(관리자는 우회 가능)로 확정**했다. 게이트의 목적이 실수 방지이지 자신을 가두는 것이 아니고, 막혔을 때 빠져나갈 길을 남겨 두는 편이 낫다고 봤다.

   대가는 분명하다. 검증 중에 확인했듯 체크가 실패한 PR은 `BLOCKED`로 표시되지만, 소유자는 GitHub의 관리자 우회로 그대로 병합할 수 있다. **지금 게이트는 소유자에게는 강제가 아니라 경고다.** 협업자가 늘어 강제가 필요해지면 이 값만 `true`로 바꾸면 되고 다른 결정에 영향이 없다.
